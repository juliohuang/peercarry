# Flutter 手机端功能规划

状态：规划，尚未创建 Flutter 工程或实现移动接口。默认先交付 Android，随后适配 iOS；不把桌面端 16 GiB 内存要求套用到手机，不内置大模型。

## 产品定位

手机与电脑之间的文本、链接、图片和文件收发工具。复用现有 Tailscale 网络和桌面 Rust 服务，日常操作不消耗模型 Token。以用户明确分享、粘贴、下载为入口，不依赖后台持续读取剪贴板。

典型路径：

1. 在浏览器、相册或文件管理器点系统“分享”→ peercarry → 选择电脑 → 发送。
2. 电脑添加文件 → 手机上打开收件箱 → 仅下载 / 下载并打开 / 分享给其他应用。
3. 手机输入需求 → 选择电脑和已配置流程 → 查看投递状态（后续阶段）。

## 页面与功能

| 页面 | 首版内容 |
| --- | --- |
| 收件箱 | 合并已添加电脑的条目；按文本、链接、图片、文件筛选；搜索、来源、大小、时间；本地收藏与已下载状态 |
| 发送 | 手动粘贴、输入文本、选择照片、拍照、选择多个文件；预览后选目标电脑；系统分享进入同一确认页 |
| 传输 | 上传/下载队列、进度、速度、剩余时间、暂停/继续/取消、失败原因、重试、磁盘空间提示 |
| 设备 | 扫码配对或手动添加 Tailscale 地址；电脑别名、连通性、默认发送目标、可选 NUC 收件箱 |
| 设置 | 下载位置、仅 Wi-Fi、蜂窝网络大文件确认、缓存上限、历史保留时间、语言、设备解绑 |

收件箱动作按内容类型展示：

- 文本：复制、编辑后发送、系统分享。
- HTTP/HTTPS 链接：默认浏览器打开、复制链接；不自动访问链接。
- 图片：预览、保存到相册、分享；复制图片按平台能力提供，不冒充所有平台均支持。
- 文件：仅下载、下载并打开、已下载后打开或系统分享。
- 邮箱/电话号码：可选“写邮件”“拨号”，只打开对应系统界面，不自动发送或拨出。
- JSON：本地格式化和复制；识别失败按普通文本处理。首版不自动执行脚本、命令或自定义 URL scheme。

手机优先采用系统分享和选择器；平板拖放作为后续增强。目录整包收发、复杂图片编辑和本地 AI 不进入首版。

## 连接与文件流向

手机安装并连接官方 Tailscale 客户端；Flutter 应用连接已配对电脑的服务，不在应用中另做 VPN。第一版手动添加地址最简单，二维码配对需桌面端新增入口，不假设手机可调用桌面 `tailscale` CLI 自动发现。

- 电脑 → 手机：拉取条目，点击下载时直接请求来源电脑；复用 HTTP Range、强 SHA-256 ETag。
- 手机 → 电脑：手机主动上传，电脑完整落盘并校验后生成条目，避免要求手机常驻开放 HTTP 服务。
- NUC 可选：手机可把文件存入 NUC，再由其他电脑下载。只有实际上传并持久保存成功的文件才可在手机离线后继续取得；只同步元数据并不能让离线来源的文件可用。
- NUC 离线或网络不可达：显示等待连接，可手动换目标，不暗中将私人内容转发到其他设备。

Tailscale 提供网络连通性，仍需目标电脑运行 peercarry 服务；移动网络不保证始终 P2P 直连，可能经中继。不能取得可靠路径信息时显示“路径未知”，不用传输速度猜测。

## 桌面协议改动

已核对当前源码：`GET /v1/hello`、`GET/POST /v1/entries`、blob 与文件下载接口可复用；`/v1/timeline`、配置和捕获接口限制在 loopback，手机不得依赖放开这些接口来工作。手机从各已配对设备的 entries 接口合并展示。

需要新建受认证约束的上传会话接口（以下为拟议名称）：

| 接口 | 含义 |
| --- | --- |
| `POST /v1/uploads` | 声明文件名、大小、SHA-256、幂等请求标识，获得上传 ID |
| `GET /v1/uploads/{id}` | 查询服务器已确认的偏移和状态 |
| `PATCH /v1/uploads/{id}` | 从指定偏移流式写入，冲突返回实际偏移；首版顺序续传 |
| `POST /v1/uploads/{id}/complete` | 校验完整内容、原子发布并生成条目；重复调用返回相同结果 |
| `DELETE /v1/uploads/{id}` | 取消会话并清理对应临时数据 |

服务器自行分配存储路径，绝不接受手机传入的磁盘绝对路径；限制单文件大小、设备配额、会话有效期和并发数。必须绑定上传会话所属设备。现有共享 token 不等于设备级配对，需要补充可撤销的设备凭据、一次性配对确认与能力协商；不能仅凭客户端自报设备 ID 实现权限隔离。

大文本、图片和普通文件统一复用上传管线，文件内容不编码进大段 JSON。旧桌面版本没有上传能力时明确提示升级，不能把只提交元数据当作上传完成。

## 下载与系统适配

状态顺序：排队 → 连接/准备 → 传输 → 校验 → 已完成；错误保留具体原因。暂停与取消分开：暂停保留可恢复数据，取消按用户选择清理。进入后台时不自动打开别的应用，完成后展示可点击通知或下次启动提示。

- 校验：流式 SHA-256，续传后核验整文件；验证成功后才标记完成。无需额外 MD5 按钮，也不将整个大文件加载进内存。
- Android：默认应用下载区；导出到用户选择的文档位置，使用系统文档 URI，不能假设拿到任意绝对路径。后台大任务通过原生任务机制适配系统版本。
- iOS：默认应用文档区，支持“存储到文件”和系统分享；可选目录授权要验证持久访问能力。后台传输交给 URLSession，强退后的恢复不作无条件保证。
- 所有平台：落盘失败、空间不足、来源修改、校验失败、权限撤销、VPN 断开必须有可理解的状态；重新启动可恢复任务记录，但是否继续运行取决于系统和来源可达性。

Android 10 起普通后台应用不能持续读取剪贴板；iOS 的程序化粘贴存在隐私提示。设计为显式“粘贴”或系统分享，避免把“无感全自动剪贴板同步”作为首版承诺。[Android 剪贴板说明](https://developer.android.com/privacy-and-security/risks/secure-clipboard-handling)、[Apple UIPasteControl](https://developer.apple.com/documentation/uikit/uipastecontrol)

Android 后台传输需按系统约束选择用户发起的数据传输任务等机制；iOS 后台会话由系统管理，用户强退会取消后台传输。[Android 任务说明](https://developer.android.com/develop/background-work/background-tasks/uidt)、[Apple 后台会话](https://developer.apple.com/documentation/foundation/urlsessionconfiguration/background(withidentifier:))

## 工程安排

建议新建 `apps/mobile/`，内含 `lib/features/{inbox,send,transfers,devices,settings}`，共享协议模型、网络层、任务库和本地存储。Flutter 负责页面与业务；分享入口、后台传输、系统文件权限使用薄原生适配层。iOS 分享扩展需要单独验证生命周期，不能只做应用内分享按钮。

首版用 Dart 实现协议客户端，不整体搬入依赖桌面系统功能的 Rust core；Rust 继续作为电脑服务。是否通过 FFI 复用纯协议模块等性能数据明确后再决定。平台调用方式参照 [Flutter Platform Channels](https://docs.flutter.dev/platform-integration/platform-channels)。

## 分阶段任务与验收

| 阶段 | 交付 | 必须通过的验收 |
| --- | --- | --- |
| M0 协议基础 | 配对、能力协商、上传会话、配额和幂等 | 无权设备被拒绝；上传中断续传；重复提交不重复生成文件；校验失败不发布 |
| M1 Android 最小版本 | 设备列表、收件箱、文本收发、图片/文件上传下载、系统分享、打开文件 | 真机 ↔ Windows 与 NUC 双向收发；中文文件名、多文件、取消选择；不自动覆盖剪贴板 |
| M2 大文件体验 | 持久队列、后台任务、暂停恢复、下载目录、通知、清理 | 1 GiB 真机传输与校验；锁屏/切后台/断网恢复；VPN 断开、空间不足；峰值内存不随文件大小线性增长 |
| M3 iOS | 共用 Flutter 业务，原生分享扩展/文件/后台适配 | iPhone 真机跑 M1/M2；另测强退、照片权限和“文件”导出；需要 macOS 构建签名环境 |
| M4 远程任务入口 | 选择电脑和流程、填需求、查看结果 | 等桌面自动化执行接口成熟后接入；限定已授权流程；区分已投递、运行中、已完成 |

先完成一个纵向场景：手机分享一张照片或一个文件到 NUC，电脑下载打开；再验证电脑的 1 GiB 文件到手机。模拟器、单元测试和 APK 构建通过不等于真机后台传输通过。开发排期在 M0 接口与 Android 设备型号明确后估算。

第一版不做远程自由点击、不执行任意命令、不依赖模型识别每一步，也不承诺后台实时收件通知。后续如需要手机长期离线提醒，需要单独设计推送或收件箱机制。
